# 計画の4ステップ（仕事は計画が10割）

タスク／プロジェクトを **「実行できる計画」** に変換する。

核となる思想（書籍『仕事は計画が10割』西村信行 / WAVE出版）:
- **計画 = 明確な目的意識と実行可能な道筋を描いた段取り**。計画が無ければ、優秀な人材も良いアイデアも力を発揮できない。
- 計画力は才能ではなく **再現可能なスキル**。下記の「型」を順に埋めれば誰でも計画できる。
- 計画とは本質的に **「現状(As-Is)とゴール(To-Be)の差分を埋める段取り」**。タスクは差分から出てくるもので、思いつきの列挙ではない。
- 計画倒れの最大原因は **STEP1の曖昧さ**（特に「やらないこと」を決めていない）。曖昧なまま先へ進めない。

詳しい背景・要約は `reference.md` を参照（必要時のみ読む）。

## 引数

`$ARGUMENTS` — 計画したいタスク／プロジェクト（例: 「新人向けオンボーディング資料を作る」）。
無い場合は「何を計画しますか？」と1問だけ聞いてから開始。

## モード（軽量版 / 重量版）

計画の重さを2モードで切り替える。**まずモードを決めてから着手する。**

- **軽量版**: 日常の軽いタスク向け。1パスでサッと。目的・ゴール・やらないこと・タスクの順番・最初の一手だけ。STEP0〜4の重い項目（クリティカルパス／リスク／キャパ突合／6W2H／振り返り等）は**省く**。
- **重量版**: 本格的なプロジェクト向け。下記STEP0〜4を全項目フルに回す。

### モードの決め方（この順で）

1. **引数で明示があれば従う**: 「軽く」「ざっくり」「さっと」「light」「軽量」→ 軽量版。「がっつり」「本格」「プロジェクトとして」「heavy」「重量」→ 重量版。
2. **明示が無ければ規模から自動判定**し、**一言告知して切替の余地を残す**:
   - 軽量版が妥当: 単発・1人・概ね1日以内・成果物が単純・他者依存が薄い
   - 重量版が妥当: 複数人 or 数日以上 or 成果物が複数 or 期限がシビア or 他者依存が強い
   - 告知例: 「これは単発タスクっぽいので**軽量版**で組みます（本格的にやるなら『重量版で』と言ってください）」
3. ユーザーがいつでも「重量版で」「軽くして」と言えば即切替。

→ 以降の STEP0〜4 と出力フォーマットは **重量版の手順**。軽量版は末尾「## 軽量版の進め方」に従う。

## 進め方の原則

- **対話は最小限・束ねて聞く**。各STEPで足りない情報だけをまとめて1回で質問する。ユーザーが「お任せ」と言えば妥当な仮置きで埋め、`(仮)` と明示する。
- **前STEPが曖昧なまま次へ進まない**。特にSTEP1のゴールと「やらないこと」が空なら必ず確定させる。
- 規模を見て粒度を調整: 半日で終わる単発タスクならSTEP0-3を軽く流す。複数人・数週間なら体制・クリティカルパス・リスクまで厚く。
- 最後は必ず **計画書(Markdown)** を出力する。口頭の要約で終わらせない。

## STEP0 — 仕事の性質を判定する

> 本書第2章「2種類の仕事と計画」。計画の立て方は仕事の性質で変わる。最初に見極める。

3分類のどれかを判定（迷ったらユーザーに一言確認）:
- **達成型（プロジェクト）**: 一度きり・終わりがある（例: 新システム導入、資料を1本作る）
- **反復型（定常業務）**: 繰り返し回す・終わらない（例: 毎月の請求処理、日次運用）
- **ハイブリッド**: 両方が混在 ← 実務の大半。

判定で以降の扱いが変わる:
| 性質 | STEP2以降の重点 |
|---|---|
| 達成型 | WBS分解 → クリティカルパス → 一度きりの納期を死守 |
| 反復型 | 標準手順化 → チェックリスト → 回す頻度/トリガー → **ボトルネック工程**の特定 → 自動化・省力化 |
| ハイブリッド | タスクを **PJ色 / 定常色に塗り分け**、それぞれ上記を適用。さらに「PJで作った成果物が定常運用にどう引き継がれるか（runbook化）」をSTEP4で必ず書く |

## STEP1 — 土台を作る（なぜ／どこまで）

> 「なぜやるのか」「どこまでやるのか」を決める。ここが計画の8割。

埋める項目:
- **目的（なぜ / Why）**: この仕事が達成したい本質。「〜のため」で言語化。
- **現状（As-Is）**: 今どうなっているか。こことゴールの差分が、STEP2のタスクの源になる。
- **ゴール（完了条件 / To-Be）**: 何がどうなったら完了か。**測定可能・観測可能**に書く（「資料が完成」ではなく「項目X・Yを含む資料がレビュー承認された」）。
- **スコープ＝やること**: ゴールに必要な範囲。
- **スコープ外＝やらないこと**: ★最重要。あえて手を出さない範囲を明示し、後で「これもやって」と崩れないよう先に線を引く。
- **関係者（Whom）**: 誰のため／誰を巻き込むか。受益者・承認者・協力者を洗い出す。
- **前提・制約**: 期限、予算、使えるリソース、守るべき条件。← これは後でリスクの源になるので控えておく。

→ ゴールと「やらないこと」が埋まるまで先に進まない。

## STEP2 — 部品をそろえる（何を）

> 「具体的に何をやるのか」を決める。現状とゴールの差分を、着手できる単位に割る。

- **分解**:
  - PJ部分 → **タスク分解(WBS)**。成果物→中タスク→実行可能単位まで。各タスクは「動詞＋目的語」で着手すれば手が動く粒度に。
  - 定常部分 → **標準手順・チェックリスト化**。毎回ブレずに回せる手順に落とす。
- **各タスクのDone基準**: 「何ができたら完了か」をタスク単位で1行。実行時の「これで終わり？」のブレを消す。
- **必要資源を「ヒト・モノ・カネ」で洗い出す**: 各タスクに誰が／何が／いくら要るか。**不足している資源（穴）を発見することがこのSTEPの目的**。
- **手段（How）**: やり方に選択肢がある場合（例: テキスト vs 動画）は手段を明記。
- **所要見積もり**: ざっくりでよいが楽観値で見ない。重要タスクは楽観/最頻/悲観の幅で持つと精度が上がる。

## STEP3 — 組み立てる（いつ・誰が・どこで・どの順番で）

> 「いつ、誰が、どんな順番でやるのか」を決める。

- **順序（依存関係）**: どのタスクが他の完了を待つか。
- **★クリティカルパス（PJ） / ボトルネック工程（定常）**: 全体の納期・スループットを決める箇所。ここの遅れ＝全体の遅れ。最優先で守る対象として**名指し**する。
- **体制（誰が）**: 各タスクの担当。1人なら自分の中の時間帯割り当て。
- **場所・環境（Where）**: どこで作業し、成果物をどこに置くか（ツール・チャネル・保管先）。定着を左右する。
- **スケジュール**: 期限から逆算してタスクを日付に置く。バッファはタスク末に散らさず**終盤にまとめて**置くと食い潰されにくい。

## STEP4 — 維持管理ルールを決める（どう守るか）

> 計画は立てた瞬間から現実とズレる。ズレを直す仕組みを先に決める。

- **進捗確認のリズム**: いつ・どの単位で見るか。**特にクリティカルパス／ボトルネック上のタスク**を重点監視。1人作業でもチェックポイントを置く。
- **遅れの早期検知（まだ遅れていない段階で兆しを掴む）**: ★結果指標（＝もう遅れた）ではなく**先行指標**を見る。**チェックポイントは締切ではなく中間点に置く**。重要タスクごとに、以下の先行指標と「黄信号の閾値」を先に決めておく:
  - **着手遅れ**: 予定着手日を過ぎても未着手（最速の予兆。まだ納期前でも分かる）
  - **ペース割れ**: 経過時間の割合 > 進捗の割合（例: 期間の50%使って進捗30%）
  - **見積超過の見込み**: 残り作業量 > 残り見積時間
  - **バッファ食い**: 終盤に置いたバッファを前倒しで消費し始めた
  - **前工程の遅れ**: 自分はまだ遅れていないが、依存している他者/前タスクが遅れ＝連鎖が確定
  - **割り込み増加**: 計画外タスクが時間を食い始めた（キャパ侵食）
  → 閾値例「バッファ半分消費 or ペース割れ20%で黄信号」。**黄のうちに動く**（赤＝遅れ確定まで待たない）。
- **遅れそう/遅れた時のリカバリ**: 遅れは結局 **スコープ・時間・リソース・品質** のどれかを動かして吸収する。健全な順で「4つのてこ」から選ぶ:
  1. **スコープを削る**（やらないことを増やす）← 最優先・最も健全。STEP1で線を引いてあるほど削りやすい
  2. **順序を組み替える**（クリティカルパス短縮・並行化）← タダで効くことがある
  3. **リソースを足す**（人・時間）← 増員は立ち上げコストで逆に遅れる罠に注意
  4. **期限を動かす**（関係者と交渉）← 早く言うほど通る
  → てこを選んだら**残りを再逆算（リスケ）**し、関係者がいれば**早めにエスカレーション**（遅れの報告は早いほど信頼を保つ）。
- **キャパ突き合わせ**: その計画は本人／チームの**他の仕事と空き時間に本当に乗るか**を確認。乗らなければスコープを削るか期限を延ばす（絵に描いた餅にしない）。
- **リスク（前提→リスク連結）**: STEP1で控えた**前提・制約が崩れる**ケースを最大のリスク源として挙げ、各々「予兆」と「起きたらどうするか」を決める。
- **変更管理**: スコープ変更・割り込みが来たときの扱い（足したら何かを削る、等）。
- **定常への引き継ぎ（ハイブリッド時必須）**: PJの成果物を定常運用のrunbook／チェックリストとしてどう渡すか。
- **振り返り→次計画への資産化**: 完了後に「見積と実績のズレ」「効いた点／崩れた点」を1行記録し、次の計画の入力にする（本書のAI活用＝過去の成功/失敗を次計画に食わせる思想）。

## 出力フォーマット（計画書）

埋めたら、以下を1枚のMarkdownで出力する:

```markdown
# 計画書: {タスク名}  （性質: 達成型 / 反復型 / ハイブリッド）

## STEP1 土台（なぜ・どこまで）
- 目的(Why):
- 現状(As-Is):
- ゴール(完了条件/To-Be):
- やること:
- やらないこと:
- 関係者(Whom):
- 前提・制約:

## STEP2 部品（何を / WBS・標準化）
| # | タスク | 性質(PJ/定常) | 担当 | モノ・カネ | Done基準 | 見積 |
|---|--------|--------------|------|-----------|----------|------|

## STEP3 組み立て（いつ・誰が・どこで・順番）
- 順序/依存:
- ★クリティカルパス / ボトルネック:
- 場所・置き場(Where):
- スケジュール（バッファは終盤集約）:

## STEP4 維持管理
- 進捗確認リズム:
- キャパ突き合わせ（乗るか）:
- リスク（前提が崩れたら→対応）:
- 変更管理ルール:
- 定常への引き継ぎ(runbook化):
- 振り返りの記録先:

## 次の一手
- いま着手すべき最初のタスク: {クリティカルパス/ボトルネックの起点}
```

## 締め前の抜け漏れチェック（軽く1回）

出力直前に以下を自己点検し、空白があれば一言補う（重い場合は指摘だけでよい）:
- **6W2H**: Why/What/Who/When/Where/Whom/How/How much に空欄が無いか
- **承認ゲート**: この計画、実行前に誰の承認が要るか（関係者がいる場合）
- **コミュニケーション**: 誰に・何を・どの頻度・どのチャネルで共有するか

最後に「**いま着手すべき最初の1タスク**」を1つだけ名指しして締める（計画を実行に橋渡しする）。

## 軽量版の進め方

日常の軽いタスク向け。**STEP0〜4の枠は使わず**、1パスで以下だけを埋める。質問は最大1回、束ねて聞く（無ければ仮置き `(仮)`）。本の思想のうち**「ゴールを観測可能に」「やらないことを決める」「最初の一手を名指し」**の3つだけは外さない。

埋めるもの:
- **ゴール（完了条件）**: 何ができたら終わりか（観測可能に1行）
- **やらないこと**: 今回やらない範囲を1行（軽量版でもここは省かない）
- **やること（順番つき）**: タスクを着手順に箇条書き。各行に必要なら担当/ざっくり見積を `(…)` で添える
- **中間チェック1点＋遅れたら**: 締切の手前に「ここまで来てるはず」の中間チェックを1つ置く。未着手 or ペース割れなら**「削るか／延ばすか」を即決**（軽量版はこの2択だけでよい）
- **最初の一手**: いま着手する1タスク

軽量版の出力フォーマット（コンパクト）:

```markdown
## {タスク名}（軽量）
- ゴール:
- やらないこと:
- 手順:
  1. …
  2. …
  3. …
- 中間チェック: {締切手前の時点}で{ここまで}／遅れてたら削る or 延ばす
- 👉 最初の一手: …
```

→ 途中で「やること」が多すぎ・他者依存が出てきた・数日かかると分かったら、**「重量版に上げますか？」と一言提案**する（軽量版の手に余るサイン）。
